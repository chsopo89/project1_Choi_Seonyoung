두 곳(로컬 로그와 로그 서버) 모두 기록되지 않는다면, 로그 서버보다는 **FortiGate 내부에서 로그가 생성·처리되지 않는 문제**를 먼저 의심하는 것이 좋습니다. Ping이 정상이어도 Syslog 포트, 출발지 IP, 라우팅, 프로세스 상태까지 정상이라는 의미는 아닙니다.

## 1. 증상 범위부터 확인

먼저 “모든 로그가 없는지” 또는 “특정 로그만 없는지”를 구분합니다.

- `Log & Report`에서 Traffic, Event, Security 로그를 각각 확인
- 최신 로그의 시간과 마지막 기록 시간을 확인
- 관리자 로그인, 정책 통과 트래픽 등 확실히 발생하는 이벤트를 만든 후 로그 생성 여부 확인
- 시간 설정이 크게 틀리면 로그가 다른 날짜로 보일 수 있으므로 NTP와 시스템 시간을 확인

CLI에서는 다음을 우선 확인합니다.

```bash
get system status
diagnose log status
```

`diagnose log status`에서 로그 장치와 로그 처리 상태가 정상인지 확인합니다. 출력 형식은 FortiOS 버전에 따라 다를 수 있습니다.

## 2. 로깅 기능과 필터 확인

전체 로깅 또는 특정 유형의 로그가 비활성화되어 있지 않은지 확인합니다.

```bash
show log setting
show full-configuration log syslogd setting
```

확인할 항목은 다음과 같습니다.

- 메모리, 디스크, FortiAnalyzer, Syslog 등의 로깅이 활성화되어 있는지
- 로그 심각도 또는 필터가 너무 제한되어 있지 않은지
- VDOM별로 로깅 설정이 다르지 않은지
- 실제 트래픽이 통과하는 정책에서 `Log Allowed Traffic`이 활성화되어 있는지
- UTM/IPS/Web Filter 로그는 해당 보안 프로파일이 실제 정책에 적용되어 있는지

정책에 문제가 없다고 판단하더라도, 테스트 트래픽이 실제로 어느 정책에 매칭되는지는 반드시 확인해야 합니다. 정책 로그가 “보안 이벤트 로그”와 동일한 것은 아닙니다.

## 3. 로컬 저장 공간과 시스템 자원 확인

로컬 로그도 생성되지 않는다면 다음을 확인합니다.

- Log & Report의 디스크/메모리 사용량
- 디스크가 가득 찼거나 오류 상태인지
- 메모리 부족, CPU 과부하, 장시간 지속된 프로세스 이상
- HA 구성이라면 현재 접속한 장비가 로그를 보관하는 장비인지
- VDOM 또는 중앙 관리 설정 때문에 다른 장비로 로그가 전달되고 있지 않은지

디스크 상태 확인 방법은 모델과 FortiOS 버전에 따라 다르므로, CLI 명령을 임의로 적용하기보다 GUI의 `Log & Report` 저장장치 상태와 `System > Dashboard` 자원 상태를 함께 확인하는 것이 안전합니다.

## 4. 로그 처리 프로세스 확인

설정과 저장 공간이 정상인데 로그가 전혀 생성되지 않으면 FortiGate의 로그 처리 프로세스 문제를 확인합니다. FortiOS에서는 일반적으로 `miglogd`가 로그 처리를 담당합니다.

유지보수 시간에 다음과 같이 디버그를 수행할 수 있습니다.

```bash
diagnose debug reset
diagnose debug application miglogd -1
diagnose debug enable
```

그 상태에서 테스트 트래픽이나 관리자 이벤트를 발생시켜 오류가 출력되는지 확인합니다. 확인 후에는 반드시 종료합니다.

```bash
diagnose debug disable
diagnose debug reset
```

오류 메시지가 없거나 프로세스가 비정상적으로 보이면 설정 백업 후 장비 재기동을 검토합니다. 다만 HA 환경에서는 페일오버 영향과 세션 영향이 있으므로 즉시 재부팅하지 말고 유지보수 절차에 따라야 합니다. 특정 FortiOS 버전의 알려진 버그일 가능성도 있으므로 버전과 릴리스 노트를 확인해야 합니다.

## 5. Syslog 전송 여부를 패킷으로 확인

로컬 로그가 정상적으로 생성되기 시작한 뒤 로그 서버 전송을 확인합니다. Ping 대신 실제 Syslog 패킷이 나가는지 확인해야 합니다.

```bash
diagnose sniffer packet any 'host <로그서버_IP> and port 514' 4 0 l
```

Syslog가 UDP 514가 아닌 TCP, TLS 또는 다른 포트를 사용한다면 실제 설정 포트로 바꿔야 합니다. 패킷 결과에 따라 다음과 같이 판단합니다.

- 패킷이 전혀 없음: 로그 생성, Syslog 설정, 필터, 프로세스 문제 가능성
- FortiGate에서 송신하지만 응답/수신이 없음: 경로, 방화벽, 서버 수신 포트 문제
- 패킷은 정상인데 서버에 저장되지 않음: 서버 측 프로토콜, 포맷, 수신 데몬 또는 파싱 문제

## 6. 출발지 IP와 라우팅 확인

Ping이 성공해도 Syslog의 출발지 IP가 다르면 서버 또는 중간 장비에서 차단될 수 있습니다.

- Syslog 설정의 `source-ip` 지정 여부
- 해당 출발지 IP에 대한 라우팅과 인터페이스
- 관리 라우팅과 일반 데이터 라우팅의 차이
- VDOM 간 또는 SD-WAN 경로 차이
- 중간 방화벽의 UDP/TCP 포트 허용 여부

결론적으로 점검 우선순위는 **로그 발생 여부 → 로컬 저장/필터 → 로그 프로세스 → 실제 Syslog 패킷 → 출발지 IP·라우팅·포트** 순서가 적절합니다. 특히 로컬 로그와 원격 로그가 동시에 사라졌다면 Syslog 서버보다 FortiGate의 로그 생성, 저장 공간, 필터 또는 `miglogd` 상태를 먼저 확인해야 합니다.
